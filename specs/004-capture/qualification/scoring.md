# ZZ-OCR-QUAL-001 scoring rules

These rules make the qualification harness deterministic. They do not set release thresholds.

## Matching

1. All image boxes use normalized image coordinates in [0,1].
2. A predicted fiducial matches a ground-truth fiducial only when roles match and IoU is at least `thresholds.fiducial_iou_threshold` in the frozen gate config. The value is greater than 0 and at most 1, and cannot be selected after final results are viewed.
3. Matching is one-to-one. Choose the assignment that maximizes total IoU. An unmatched prediction is a false finder. An unmatched truth endpoint is a missed endpoint.
4. A predicted pair is correct only when its matched opening and closing endpoints share the same ground-truth pair_id. Otherwise it is a false pair.
5. Multi-code images are scored per ground-truth pair. Every `ground_truth_codes` entry is keyed by `pair_id` and carries the literal payload used for CER/part scoring plus the canonical code when valid. Merging two codes into one ROI is not correct.

Endpoint precision is matched endpoints / predicted endpoints; endpoint recall is matched endpoints / ground-truth endpoints. Complete-pair detection is the number of complete ground-truth pairs whose opening and closing endpoints both matched, divided by complete ground-truth pairs; it does not imply the recognizer grouped those endpoints correctly. Pair accuracy is correctly linked predicted pair IDs / all non-null predicted pair IDs. False-pair rate is false predicted pair IDs / all non-null predicted pair IDs, including malformed groups with a missing or duplicate endpoint. Each rate is null only when its denominator is zero.

The reusable implementation in `scripts/ocr-qualification-matching.mjs` computes normalized rectangle IoU, role-constrained maximum-weight one-to-one fiducial assignment, and reconciliation of predicted endpoint pair IDs against those assignments. Pair reconciliation keeps complete endpoint detection separate from correct pairing and marks crossed or malformed predicted groups as false pairs. Unknown-role predictions are retained as unmatched evidence and cannot become a correct pair. Tests cover greedy-assignment counterexamples, threshold boundaries, role mismatches, crossed pairings, unknown-role evidence, and invalid assignments/geometry.

`scripts/ocr-qualification-fiducial-scoring.mjs` converts assignments into endpoint precision/recall, false-finder and missed-endpoint counts, complete-pair detection, pair accuracy, and false-pair counts/rates. `scripts/ocr-qualification-fiducial-aggregation.mjs` aggregates them by split, device/split, and stress-bucket/split using summed numerators and denominators with count reconciliation and overflow checks. `scripts/ocr-qualification-roi-latency.mjs` scores convex normalized ROI polygons by pair ID, gives missing truth-pair predictions IoU 0, computes rectification success separately, and computes conventional median and nearest-rank p95 from sample `elapsed_ms`. `scripts/ocr-qualification-roi-latency-aggregation.mjs` recomputes weighted ROI, rectification, and latency metrics from observations for the same groupings.

`scripts/ocr-qualification-fiducial-aggregation.mjs` aggregates those endpoint/pair rate numerators and denominators by split, device/split, and stress-bucket/split. It counts each device/sample observation once in a group, rejects duplicate device/sample rows, inconsistent per-sample count/rate fields, and unsafe count overflow, and is consumed by the diagnostic scoring pipeline.

`scripts/ocr-qualification-roi-latency-aggregation.mjs` weights ROI mean IoU by truth-pair count, recomputes rectification success from counts, and derives p50/nearest-rank p95 from concatenated per-sample elapsed times for the same split/device/bucket groupings. A group with any unmeasured rectification outcome retains a null rate, and missing latency remains null. The diagnostic scoring pipeline uses it for the final gate evaluator and the incomplete receipt projection.

`scripts/ocr-qualification-text-scoring.mjs` accepts only correctly linked pair IDs, preserves candidate engine order and uses top-1, computes exact-code accuracy for valid canonical truth, computes the frozen descriptive part/word metric, aggregates NFC-normalized Unicode code-point Levenshtein edits against literal payload truth, and counts false-valid observations only when top-1 replay is a different check-word-valid plain code. Missing or unpaired hypotheses contribute an empty CER prediction and an incorrect exact-code observation; they remain in the false-valid denominator with no false-valid numerator. `scripts/ocr-qualification-text-aggregation.mjs` aggregates these outcomes by split, device/split, and stress-bucket/split and recomputes rates from summed counts.

`scripts/ocr-qualification-scoring-pipeline.mjs` connects the scorers and aggregators with pinned decoder band replay, validates exact device/sample coverage, checks minimum tuning/final split sample counts, projects diagnostic `metric_sets` in the receipt metric-set shape by split/device/bucket, and returns final-only results from `scripts/ocr-qualification-gates.mjs`. Wrapped-code and multi-code accuracy are sample-level exact-success rates over tagged samples with valid truth; no-code false-positive rate uses bare/no-code sample observations as its denominator. Crash and exception counts come from explicit adapter runtime outcomes; failed runtime rows must contain no OCR evidence and are excluded from band distribution rather than assigned a fabricated decision. Runtime memory is max measured sample memory only when every row in the group has a value. Package-size delta remains explicitly not measured until a baseline is frozen. The gate evaluator enforces the eight fixed gate IDs, uses the maximum final p95 across the frozen device matrix, and returns `INCOMPLETE` for missing measurements. The preflight invokes scoring only after structural validation, replay, and decoder-identity checks pass, but remains `INCOMPLETE` / `NO_PROMOTION`; a `PASS` label for numeric gates is not qualification approval.

The metric-set projection remains diagnostic and cannot authorize qualification. It emits wrapped/multi-code and no-code rates, crash/exception counts, memory/package fields, and per-device coverage diagnostics; package-size delta is null with a reason until a baseline is frozen. The preflight now assembles and validates a hash-addressed receipt/report artifact when scoring succeeds. That artifact is always `INCOMPLETE`, carries no promoted engine, approver, or PR, uses explicit blocked/unassigned review and case dispositions, and cannot authorize promotion. Missing verified freeze time remains null. Receipt assembly or semantic validation failure leaves the artifact unavailable and adds an explicit preflight reason. CLI stdout is an aggregate-only projection: per-sample OCR/case details are omitted, and complete receipt evidence is written only to explicitly requested private files. Outputs are atomically replaced with mode `0600`, including when a prior file exists, and duplicate output destinations are rejected. This is harness plumbing, not a qualification result: protected workflow/attestation enforcement, private corpus ingress, actual trusted-time verification, real signature verification, independent human review, and device evidence remain release blockers.

## ROI and rectification

Where ROI ground truth exists, report polygon localization IoU/error before rectification and rectification success separately from payload OCR errors. Match predicted and ground-truth ROIs by fiducial `pair_id`; assignments are one-to-one. If a manifest case requires ROI truth and it is absent, the manifest is invalid. If a prediction or metric is unavailable, record the explicit null/not-measured reason; do not silently omit the metric.

ROI polygons must be simple, convex, consistently ordered polygons in normalized `[0,1]` image coordinates; unsupported or degenerate geometry invalidates scoring rather than being approximated. For each device/split set, mean ROI IoU is over all ground-truth ROI pairs; a missing prediction contributes IoU 0, while predictions without truth do not enter this denominator. Rectification success is successful truth-paired predictions / truth ROI count; a missing prediction is a failure. If any matched prediction lacks an explicit `rectification_succeeded` boolean, the rectification rate for that set is null and its pair IDs are recorded as not measured. No-truth sets report null ROI and rectification metrics.

## Text and code scoring

1. Preserve raw recognizer text for CER and part scoring.
2. Exact-code accuracy compares each decoded code with the canonical truth having the same `pair_id`; an unkeyed or cross-paired comparison is invalid.
3. CER uses Levenshtein edit distance between each candidate's recognizer text and the `literal_payload` for the same `pair_id`; both fields contain payload text only, without the structural boundary markers. The frozen gate config pins `cer_normalization` to `nfc-code-points-v1`: normalize both strings to Unicode NFC and count Unicode code points without case-folding, trimming, whitespace collapsing, punctuation removal, or wordlist correction. Partial and invalid cases retain literal payload truth even when `canonical_code` is null. Any other normalization requires a new protocol version.
4. `part_word_accuracy` is descriptive and is not a v1 release gate. Normalize reference and top-1 payload to Unicode NFC, split each on Unicode whitespace, and discard empty tokens. Compare the ordered token sequences with unit-cost Levenshtein edit distance; token equality is exact after NFC (no case folding, punctuation stripping, whitespace correction within tokens, or wordlist correction). For `N` reference tokens and edit distance `D`, report numerator `max(0, N - D)`, denominator `N`, and their ratio. Insertions therefore reduce accuracy, and a missing hypothesis scores zero for a non-empty reference. If the reference contains no tokens, report a null rate with a zero denominator. Any alternate tokenizer or alignment is a new protocol version.
5. Count a false-valid decode for a `(device_matrix_entry_id, sample_id, pair_id)` observation when top-1 replay is syntactically and check-word valid but differs from that pair's valid canonical ground truth. This metric is independent of runtime disposition: a multi-hypothesis ROI still yields runtime `CLARIFY`, while its first engine-ordered hypothesis is used only for the gated false-valid measurement. A missing hypothesis contributes one denominator unit and zero numerator. Pairs without valid canonical truth are excluded from this denominator.
6. Count False Accept whenever product state is Accept and the selected canonical code is not ground truth, or the sample has no valid ground-truth code.
7. Multiple candidates are not an error by themselves when the product requires a person to pick. Score them against expected band constraints and pair accuracy.

8. Candidate order is the recognizer's returned order and is immutable through serialization. Do not sort by confidence, validity, wordlist proximity, or ground truth. If one ROI has more than one text hypothesis, runtime disposition is `CLARIFY` and the UI presents hypotheses in the preserved order; no hypothesis is silently selected. For scoring, replay each candidate independently, but define the primary decoded outcome as top-1 (the first engine-ordered hypothesis). Exact-code accuracy, part/word accuracy, and CER use top-1; a missing hypothesis is an incorrect exact-code result, contributes an empty prediction for CER, and scores zero part/word accuracy for a non-empty reference. For false-valid-decode, each `(device_matrix_entry_id, sample_id, pair_id)` observation with a complete valid ground-truth code is one denominator unit, including observations with no OCR hypothesis; the numerator counts observations whose top-1 replay is a different valid code. Never collapse the same sample across device-matrix entries. Additional hypotheses are descriptive only and never affect gated metrics. Ground truth is scorer-only and must not affect candidate ordering, selection, or runtime state.

## Aggregation

Report separate `tuning` and `final` metric sets. Each set reports overall and per-stress-bucket: numerator, denominator, and rate for every rate metric; endpoint precision/recall; complete-pair detection; pair accuracy; false finders/pairs; exact-code and part/word accuracy; CER; false-valid and False Accept; band distribution; median and p95 latency. The receipt also reports the complete metric set separately for every device-matrix entry and split, so no device's failure can be hidden by aggregate results. Never merge or average split metrics. Release-gate observations, False Accept/false-valid dispositions, and pass/fail decisions are computed from the final split only; tuning metrics are descriptive and cannot contribute to release gates.

The `p95-latency-ms` gate's observed value is the maximum per-entry final-split p95 across the entire frozen device matrix. Every entry must have a measured final p95 and each must be at or below `max_p95_latency_ms`; an aggregate or bucket p95 cannot mask a slow device entry. In a receipt, a null per-entry p50 or p95 explicitly means that measurement was not available; the semantic guard accepts the JSON shape but an unmeasured final p95 makes qualification INCOMPLETE.

Latency uses the adapter's non-negative per-sample `elapsed_ms`. `p50` is the conventional median (mean of the middle pair for even counts); `p95` uses nearest rank at sorted index `ceil(0.95 * n) - 1`. Empty latency groups are not measured and cannot satisfy the p95 gate.

Compute overall rates from overall numerators and denominators. Do not average bucket percentages.

## Input and receipt consistency checks

The validator applies these checks in addition to JSON Schema:

1. The gate config's `manifest_sha256` and adapter-result `manifest_sha256` equal the exact whole-corpus manifest byte hash. Hash the device matrix's canonical JCS bytes and require equality with the hash in the candidate bundle, adapter results, execution attestation, and receipt. The matrix's `candidate_id` and `platform` equal the sealed candidate bundle's values; matrix entry IDs are unique. Adapter-result `candidate_id` and `candidate_bundle_sha256` equal the sealed bundle and attestations; its adapter commit, platform, engine/version, artifact, config, preprocessing, confidence-mapping, and device-matrix identities equal the bundle field-for-field. Every result's device-matrix entry ID, OS version, and device class match exactly one entry in the frozen matrix. For every matrix entry, every manifest sample appears exactly once (keyed by entry ID plus sample ID); no extra/duplicate pair is permitted, split and image hash equal the manifest entry, and device coverage meets that entry's frozen minimum.
2. The set of `writer_group` values in tuning is disjoint from the set in final. Any overlap invalidates the corpus and makes the run INCOMPLETE.
3. Every ground-truth code entry has a unique `pair_id` within its sample. Complete truth pairs map to exactly one opening and closing fiducial. Each `roi_truth.pair_id` maps to a complete ground-truth fiducial pair, and each complete visual pair has exactly one ROI truth. Polygon points and boxes remain within the normalized image; the scorer rejects geometry extending outside the image.
4. Before final execution, canonicalize the frozen candidate-bundle JSON as RFC 8785 JSON Canonicalization Scheme (JCS) and hash those canonical bytes with SHA-256. Verify the exact JCS bytes of each unsigned attestation using the detached Sigstore Cosign bundle supplied as a separate validation input. The verifier uses the Sigstore public-good TUF trust root bootstrapped independently of candidate files and the allowlist in `.github/ocr-qualification-verifier-policy.json`: Cosign `v3.1.3`, GitHub Actions OIDC issuer `https://token.actions.githubusercontent.com`, exact identity `https://github.com/Zero-State-LLC/zzthis/.github/workflows/ocr-qualification.yml@refs/heads/main`, and one v0.3 bundle transparency entry. The verifier must use an isolated environment so caller-provided trust-root overrides cannot change trust. Require Cosign cryptographic verification, a valid Rekor inclusion proof, and signed entry timestamp for both attestations. The trusted workflow must gate final-process start on successful pre-run publication and capture start/finish from its runner clock, rejecting caller-provided times. The pre-run Rekor timestamp is the trusted publication/freeze time; the signed execution payload binds the same bundle hash, pre-run hash, device-matrix hash, and exact adapter-results hash, and its declared `started_at_utc` must follow that pre-run time. The execution bundle's Rekor timestamp must be no earlier than its signed `finished_at_utc`. For other input files, hash exact bytes. Caller-supplied timestamps or publication URLs are not evidence. Missing, invalid, mismatched, untrusted, or backdated attestations make the run INCOMPLETE. A separate RFC 3161 TSA is not required for v1; adding one requires a distinct trust-policy decision. A verifier helper and policy file alone are not evidence of a trusted workflow: the policy must be protected on `main`, and workflow identity/repository protections must be verified before final execution is enabled.
5. `split_counts`, per-split aggregate sample counts, and per-split bucket counts reconcile to the manifest and result set. Each split meets `minimum_samples_by_split`. The frozen gate config must require every canonical stress bucket, each with a positive minimum count, and the observed final count for each required bucket must meet that minimum. Missing or under-count coverage is INCOMPLETE.
6. For every rate in each split, numerator and denominator match counted observations; rate is numerator / denominator, or null only when denominator is zero. Count fields equal the corresponding case lists. Band counts sum to that split's sample count.
7. Every final-split False Accept and false-valid case is listed with its device-matrix entry, sample, pair (null only for a sample-level/no-code False Accept), expected/observed values, and a non-empty reviewer disposition. False-valid case keys are unique `(device_matrix_entry_id, sample_id, pair_id)` observations; no undispositioned case is allowed in PASS. Any observed False Accept or false-valid case forces `NO_PROMOTION`, even when its disposition is complete or its measured rate is within a nonzero configured ceiling.
8. `receipt.candidate_id`, candidate-bundle hash, pre-run/execution attestation hashes and bundle hashes, gate-config hash, manifest hash, and device-matrix hash match the exact frozen inputs. Candidate id and bundle hash agree across the bundle, both attestations, adapter results, and receipt. Every adapter/decoder identity field in the receipt equals the sealed bundle. `device_coverage` has exactly one row per frozen matrix entry and its environment, required/observed sample counts, and complete per-split metric sets reconcile exactly to the adapter results. False-valid disposition keys equal the final-split numerator observations; no duplicate key is permitted. `release_gates.frozen_at_utc` is copied from the verified pre-run Rekor timestamp, not supplied by the caller. Receipt `run_id`, `started_at_utc`, and `finished_at_utc` equal the signed execution attestation fields; the declared start follows the pre-run publication time and the execution bundle's verified Rekor timestamp is no earlier than finish. `required_gate_ids` equals the protocol's fixed set exactly, and `gate_results` contains each id exactly once with `split: final`; its observed value/comparator/threshold recompute to the recorded result using the gate-config threshold mapping and pinned IoU/CER normalization parameters. The p95 latency gate uses the maximum final-split p95 across all frozen matrix entries and passes only if every entry is at or below threshold.
9. Adapter input contains evidence only. Candidate `confidence` is the conservative minimum meaningful confidence over all payload parts, including the check word; where only line-level values exist, each token inherits its line's value before taking the minimum. If no meaningful confidence is available, preserve `confidence_status: not-available` and `confidence: null`; never synthesize a value. Gate config freezes `accept_min_confidence` and `retry_below_confidence`, with retry strictly below accept. Stress-bucket labels such as blur or glare are not themselves runtime capture issues; only explicit missing-fiducial reason codes, no candidate, or a separately mapped capture issue can force Retry. The decoder identity scopes are exact: `decoder.commit` is the full Git commit of the clean checkout used for replay; `wordlist_sha256` hashes the exact bytes of `packages/zz-core/src/generated/wordlists.ts`; `checkword_sha256` hashes `packages/zz-core/src/checkword.ts`; `vectors_sha256` hashes `specs/003-wordlist-checkword/vectors.json`; and `band_mapping_sha256` hashes `specs/004-capture/qualification/decision-band-mapping.json`. Component file hashes use SHA-256 on raw file bytes, without text normalization or JSON canonicalization. The commit pins executable parser, classifier, check-word, and band code. Before replay can be marked `EXECUTED_PINNED`, the harness independently recomputes all four file hashes, verifies the full checkout commit, and requires a clean worktree; any unavailable, dirty, or mismatched identity keeps replay unpinned and the run INCOMPLETE. The harness derives decoded codes, canonicalization, validity, and product state by replaying every candidate through that pinned implementation, wordlist, vectors, and band mapping. For each valid manifest truth entry, the validator reconstructs the marked candidate from `literal_payload`, parses it with that same pinned decoder, and requires equality with `canonical_code`; any mismatch invalidates the manifest and makes the run INCOMPLETE. Resolver state and ground truth never change candidate selection or decoding.
10. PASS is valid only for a non-empty final split, disjoint writer groups, complete schema-valid evidence, verified matching attestations, all required bucket minima met, passing final-only release gates, zero final False Accepts and zero final false-valid cases, and approved dependency/license, privacy, security, and qualification reviews. The approver, promoted engine, and linked PR must be present. Otherwise the only valid disposition is FAIL, INCOMPLETE, or NO_PROMOTION, with no promoted engine.
11. Results are evaluated offline. The validator must not resolve codes over the network or use server state to alter any metric.

## Final split discipline

Freeze the manifest, gate config, adapter candidate, and decoder identity in a verifiable signed pre-run attestation before final execution. The trusted execution attestation binds the exact results and start time. Evaluate the final split once per sealed candidate. A corpus, gate config, code, or configuration change after viewing final results creates a new candidate and receipt. Previous attestations and receipts remain immutable evidence. A caller-entered timestamp or hash without verifiable publication and signature can never support PASS.

The required gate IDs and threshold mapping are fixed by protocol: `false-accept-count` → `max_false_accept_count` (`lte`); `false-valid-decode-rate` → `max_false_valid_decode_rate` (`lte`); `endpoint-recall` → `min_endpoint_recall` (`gte`); `pair-accuracy` → `min_pair_accuracy` (`gte`); `exact-code-accuracy` → `min_exact_code_accuracy` (`gte`); `character-error-rate` → `max_character_error_rate` (`lte`); `rectification-success-rate` → `min_rectification_success_rate` (`gte`); and `p95-latency-ms` → `max_p95_latency_ms` (`lte`). The validator rejects omitted, duplicate, unknown, or tuning-split gate results, as well as a comparator or threshold inconsistent with this mapping.

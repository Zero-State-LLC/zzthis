# ZZ-OCR-QUAL-001 local runner setup

The protected workflow at `.github/workflows/ocr-qualification.yml` evaluates frozen qualification evidence on a local macOS/ARM64 runner. It is diagnostic-only and never authorizes camera Accept, engine promotion, or production deployment.

## Required GitHub configuration

Before dispatching the workflow:

1. Create the organization runner group `zzthis-ocr-qualification` and restrict its repository access to `Zero-State-LLC/zzthis`. Restrict workflow access to this exact protected-main workflow if the organization plan supports workflow-level runner-group restrictions.
2. Register a dedicated, continuously updated self-hosted runner in that group with labels `self-hosted`, `macOS`, `ARM64`, and `ocr-qualification`. Do not reuse a runner from the organization-wide Default group for private qualification data. Keep the runner account separate from interactive personal use and do not place unrelated secrets or source checkouts under its service account.
3. Configure repository variable `ZZ_OCR_QUAL_PRIVATE_ROOT` to an absolute, owner-only directory outside the checkout. The variable contains a path, not a credential. The runner process must be able to read and write this path.
4. Provision Node.js 22.12 or newer and Cosign exactly `v3.1.3` in the runner service environment. Pin and update these tools through the runner-maintenance process; the workflow checks their versions and does not download Cosign.
5. Protect `main` with required review and status checks. Keep `.github/ocr-qualification-verifier-policy.json` and the workflow identity policy protected on `main`. The policy allowlists only this workflow on `refs/heads/main`.

The current organization inventory showed only two online macOS/ARM64 runners in the shared Default group and no repository-scoped runner. Those runners are not an approved execution target for this workflow. The dedicated group and path variable remain external prerequisites until configured and verified.

## Private directory layout

Create one directory per opaque candidate ID. All directories must be owned by the runner account and have no group/world permissions; source files must be regular files with no group/world permissions. Do not use symlinks.

```text
<ZZ_OCR_QUAL_PRIVATE_ROOT>/
  candidates/
    <candidate-id>/
      manifest.json
      device-matrix.json
      candidate-bundle.json
      gate-config.json
      adapter-results.json
      pre-run-attestation.json       # generated in `freeze` stage
      pre-run-bundle.sigstore.json   # generated by keyless Cosign
  runs/
    <GITHUB_RUN_ID>.<GITHUB_RUN_ATTEMPT>/
      execution-attestation.json    # generated after local evaluation
      execution-bundle.sigstore.json
      qualification-diagnostic.json
      qualification-diagnostic.md
      qualification-receipt.json
      qualification-receipt.md
```

The manifest, gate config, candidate bundle, matrix, and adapter results are read as inputs; the workflow never uploads them. The signed attestations contain hashes, candidate identity, run identity, and times. Sigstore publishes the signed attestation payloads and their hashes/transparency metadata, not photographs or per-sample results. The raw corpus remains on the local runner's encrypted storage under the separate corpus-control procedure; no images are copied into Git, the checkout, Actions artifacts, workflow logs, or summaries.

## Two-stage operation

1. Dispatch `OCR Qualification (local, diagnostic only)` on protected `main` with stage `freeze` and the candidate ID. The workflow binds exact manifest/gate bytes and JCS candidate/matrix identities, creates and keyless-signs the pre-run attestation, then verifies its own Sigstore bundle and Rekor evidence.
2. After confirming the frozen files have not changed, dispatch the same workflow with stage `evaluate` and the same candidate ID. It re-verifies the pre-run signature and bindings before timing local replay/scoring, captures start/finish itself, creates and signs the execution attestation, and runs the diagnostic receipt validator against the exact frozen inputs.
3. Inspect the resulting files directly on the local runner under `runs/<run-id>.<attempt>/`. The GitHub Actions result means only that a non-authorizing diagnostic receipt was assembled. Do not interpret it as qualification PASS; this workflow intentionally requires `INCOMPLETE` / `NO_PROMOTION` and publishes no evidence files.

If a freeze, signature, verification, decoder-identity, or scoring step fails, stop and preserve the candidate directory for investigation. Do not edit frozen inputs in place after signing. Any change requires a new candidate ID and newly published pre-run attestation. Do not copy the private directory into a PR, issue, Actions artifact, or general-purpose runner.

## Scope limit

This stage consumes a serialized `adapter-results.json`. It currently does not drive Apple Vision, ML Kit, PP-OCR, a camera, or a physical device. T003/T003A and the native-capture tasks remain incomplete until adapter execution/result generation, the dedicated runner group, representative-device evidence, independent review, and all privacy/security/qualification gates are implemented and verified.
